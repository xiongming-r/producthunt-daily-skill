# v0.2 Roadmap: Broader Leaderboards And Agent Integrations

## Goal

v0.2 expands v0.1 from a daily collector into a broader Product Hunt intelligence worker. It should support daily, weekly, monthly, and yearly collection modes, richer Product Hunt filtering, keyword/topic-driven discovery, and deeper integration with WorkBuddy, Qclaw, Hermes, Codex, and Claude Code.

## Product Hunt API Capabilities To Use

Based on Product Hunt API v2 GraphQL documentation:

- `posts` query arguments include `featured`, `order`, `postedAfter`, `postedBefore`, `topic`, `url`, and `twitterUrl`.
- `Post` includes ranking fields such as `dailyRank`, `weeklyRank`, `monthlyRank`, and `yearlyRank`.
- `topics` query supports topic discovery by search query.
- Product Hunt API uses a complexity-based rate limit, so broader collection modes should avoid unnecessary over-fetching.

Official references:

- `https://api-v2-docs.producthunt.com/query/posts/`
- `https://api-v2-docs.producthunt.com/object/post/`
- `https://api-v2-docs.producthunt.com/query/topics/`
- `https://api-v2-docs.producthunt.com/introduction/rate-limits/`

## Scope

### 1. Collection Periods

Add a period concept:

```text
daily
weekly
monthly
yearly
```

CLI examples:

```bash
ph-daily collect --period daily --date today
ph-daily collect --period weekly --date 2026-05-11
ph-daily collect --period monthly --date 2026-05-01
ph-daily collect --period yearly --date 2026-01-01
```

The `--date` value is the anchor date. The collector derives the date range:

- daily: one UTC day.
- weekly: the week containing the anchor date.
- monthly: the month containing the anchor date.
- yearly: the year containing the anchor date.

### 2. Period-Specific Defaults

The larger the period, the stricter the default thresholds.

Recommended defaults:

| Period | Min Votes | Min Comments | Comment Ratio | Fetch Limit |
| --- | ---: | ---: | ---: | ---: |
| daily | 300 | 8 | 0.04 | 100 |
| weekly | 800 | 20 | 0.035 | 150 |
| monthly | 1000 | 40 | 0.03 | 200 |
| yearly | 5000 | 120 | 0.02 | 300 |

Suggested env variables:

```env
DAILY_MIN_VOTES=300
WEEKLY_MIN_VOTES=800
MONTHLY_MIN_VOTES=1000
YEARLY_MIN_VOTES=5000

DAILY_MIN_COMMENTS=8
WEEKLY_MIN_COMMENTS=20
MONTHLY_MIN_COMMENTS=40
YEARLY_MIN_COMMENTS=120

DAILY_COMMENT_RATIO=0.04
WEEKLY_COMMENT_RATIO=0.035
MONTHLY_COMMENT_RATIO=0.03
YEARLY_COMMENT_RATIO=0.02
```

Keep the existing generic `MIN_VOTES`, `MIN_COMMENTS`, and `COMMENT_RATIO` as fallback values for backward compatibility.

### 3. Product Hunt Filters

Support filters that map to official Product Hunt `posts` arguments:

- `featured`: only featured posts or all posts.
- `topic`: Product Hunt topic slug.
- `order`: supported Product Hunt post ordering.
- `postedAfter` and `postedBefore`: derived from period and date, with manual override only if needed.
- `url` and `twitterUrl`: optional exact filters for diagnostic/single-product cases.

Possible CLI examples:

```bash
ph-daily collect --period monthly --topic artificial-intelligence
ph-daily collect --period weekly --featured true
ph-daily collect --period daily --order VOTES
```

### 4. Keyword And Topic Filtering

Add local keyword filtering after Product Hunt fetch and before LLM enrichment.

Suggested config:

```env
INCLUDE_KEYWORDS=ai,agent,developer tools
EXCLUDE_KEYWORDS=crypto,gambling
TOPIC_SLUGS=artificial-intelligence,developer-tools
```

Matching fields:

- product name
- tagline
- description
- topics

Keyword filtering should be case-insensitive. Products matching `EXCLUDE_KEYWORDS` should be removed even if they match an include keyword.

Topic support should have two layers:

1. pass topic slugs to Product Hunt when available;
2. optionally use local topic/name/tagline matching for broader search.

### 5. Output Naming

Use period-aware output paths:

```text
data/raw/daily/YYYY-MM-DD.json
data/raw/weekly/YYYY-WW.json
data/raw/monthly/YYYY-MM.json
data/raw/yearly/YYYY.json

reports/daily/YYYY-MM-DD.md
reports/weekly/YYYY-WW.md
reports/monthly/YYYY-MM.md
reports/yearly/YYYY.md
```

For backward compatibility, daily output can continue writing the current v0.1 paths unless a migration is explicitly chosen.

## Agent And Skill Integration

### Shared Principle

Keep the deterministic collector script. Agent integrations should orchestrate, monitor, retry, and summarize. They should not duplicate core Product Hunt filtering or storage logic.

### LLM Layer As Agent

v0.2 should evaluate making the enrichment layer pluggable:

```text
Script mode:
  Collector -> OpenAI-compatible LLM HTTP endpoint

Agent mode:
  Collector -> enrichment provider interface -> Agent runner -> structured JSON enrichment
```

Keep script mode as the default because it is easier to deploy on cron and cloud servers.

### Common Agent Adapter Shape

Define a shared adapter contract:

```python
class EnrichmentProvider:
    def enrich_product(self, product: Product) -> ProductEnrichment:
        ...
```

Then provide adapters or docs for:

- OpenAI-compatible HTTP provider.
- Codex automation wrapper.
- Claude Code command wrapper.
- Hermes endpoint/provider.
- WorkBuddy command integration.
- Qclaw command integration.

### WorkBuddy And Qclaw

Likely integration pattern:

- expose CLI commands as callable tasks;
- let the tool invoke `ph-daily collect`;
- let the tool read generated Markdown/HTML/processed JSON;
- let the tool report summary and failures.

Shared task prompt:

```text
Run Product Hunt collection for the requested period. If it succeeds, report selected count and generated report paths. If it fails, inspect stderr/stdout and processed JSON if available, then summarize the failure without exposing secrets.
```

### Hermes

Hermes can be:

1. a scheduler that calls CLI commands;
2. an OpenAI-compatible endpoint used by the existing LLM HTTP adapter;
3. an agent-like enrichment provider if it can return strict JSON matching `ProductEnrichment`.

### Codex And Claude Code

Recommended v0.2 deliverables:

- `docs/agent-integration-codex.md`
- `docs/agent-integration-claude-code.md`
- reusable prompt templates for:
  - daily collection
  - weekly/monthly/yearly collection
  - failed enrichment rerun
  - report summarization
- optional local skill files if the target host supports skill packaging.

## Suggested v0.2 Tasks

1. Add `Period` model and date-range calculation.
2. Add period-specific threshold settings.
3. Extend Product Hunt client filters according to official `posts` arguments.
4. Add keyword/topic include/exclude filtering.
5. Add period-aware CLI options and output paths.
6. Add tests for daily/weekly/monthly/yearly filtering.
7. Add agent integration docs and prompt templates.
8. Evaluate and prototype an `EnrichmentProvider` abstraction.
9. Add one script-mode provider and one agent-mode provider proof of concept.

## Open Questions

- Should weekly/monthly/yearly output keep v0.1 daily paths for backward compatibility, or move all periods into period-specific directories?
- Should v0.2 fetch all pages up to API/rate limits, or keep configurable `FETCH_LIMIT` per period?
- Which exact Product Hunt topic slugs matter most for the first keyword/topic preset?
- Which agent should be implemented first as a real adapter rather than documentation-only integration?

# v0.2 路线图：扩展榜单与 Agent 集成

## 目标

v0.2 将 v0.1 从“日榜采集器”扩展为更完整的 Product Hunt 情报采集 worker。它需要支持日榜、周榜、月榜、年榜，更丰富的 Product Hunt 官方过滤条件，关键词/topic 过滤，以及 WorkBuddy、Qclaw、Hermes、Codex、Claude Code 的更深层集成。

## Product Hunt API 能力

基于 Product Hunt API v2 GraphQL 文档：

- `posts` 查询参数包括 `featured`、`order`、`postedAfter`、`postedBefore`、`topic`、`url`、`twitterUrl`。
- `Post` 字段包括 `dailyRank`、`weeklyRank`、`monthlyRank`、`yearlyRank`。
- `topics` 查询支持按 query 搜索 topic。
- Product Hunt API 使用复杂度限流，因此更大周期的采集需要避免无意义过量拉取。

官方参考：

- `https://api-v2-docs.producthunt.com/query/posts/`
- `https://api-v2-docs.producthunt.com/object/post/`
- `https://api-v2-docs.producthunt.com/query/topics/`
- `https://api-v2-docs.producthunt.com/introduction/rate-limits/`

## 采集周期

新增 period 概念：

```text
daily
weekly
monthly
yearly
```

CLI 示例：

```bash
ph-daily collect --period daily --date today
ph-daily collect --period weekly --date 2026-05-11
ph-daily collect --period monthly --date 2026-05-01
ph-daily collect --period yearly --date 2026-01-01
```

`--date` 是锚点日期，程序根据它计算日、周、月、年的时间范围。

## 周期默认阈值

周期越大，默认筛选越严格：

| 周期 | 最低票数 | 最低评论数 | 评论比例 | 抓取上限 |
| --- | ---: | ---: | ---: | ---: |
| daily | 300 | 8 | 0.04 | 100 |
| weekly | 800 | 20 | 0.035 | 150 |
| monthly | 1000 | 40 | 0.03 | 200 |
| yearly | 5000 | 120 | 0.02 | 300 |

建议新增环境变量：

```env
DAILY_MIN_VOTES=300
WEEKLY_MIN_VOTES=800
MONTHLY_MIN_VOTES=1000
YEARLY_MIN_VOTES=5000
```

保留 v0.1 的 `MIN_VOTES`、`MIN_COMMENTS`、`COMMENT_RATIO` 作为兼容 fallback。

## 过滤能力

优先支持 Product Hunt 官方 `posts` 查询参数：

- `featured`
- `topic`
- `order`
- `postedAfter`
- `postedBefore`
- `url`
- `twitterUrl`

再增加本地关键词过滤：

```env
INCLUDE_KEYWORDS=ai,agent,developer tools
EXCLUDE_KEYWORDS=crypto,gambling
TOPIC_SLUGS=artificial-intelligence,developer-tools
```

关键词匹配字段：

- 产品名
- tagline
- description
- topics

`EXCLUDE_KEYWORDS` 优先级高于 `INCLUDE_KEYWORDS`。

## Agent 与 Skill 化

v0.2 不应该放弃当前脚本能力。推荐做成双模式：

```text
脚本模式：
  Collector -> OpenAI-compatible LLM HTTP endpoint

Agent 模式：
  Collector -> EnrichmentProvider -> Agent runner -> strict JSON enrichment
```

共同抽象：

```python
class EnrichmentProvider:
    def enrich_product(self, product: Product) -> ProductEnrichment:
        ...
```

优先适配：

- WorkBuddy
- Qclaw
- Hermes
- Codex
- Claude Code

这些工具的共同点是：可以调度命令、读取产物、报告结果。因此第一层集成应优先文档化和 prompt 模板化；第二层再做真正的 enrichment provider / skill 包装。
